# trendai 웹 앱 — 디자인 리서치 & 디자인 브리프

작성일 2026-11-25 · 대상: trendai(CLI·HTML 리포트)를 **한국어 우선(영어 전환 가능) 웹 앱**으로 만드는 작업 ·
상태: 구현 착수용 결정안. 설계 결정 옆의 `[G4]`·`[K1]` 같은 표기는 **부록 A 근거 목록**의 항목 번호입니다(출처 URL과 확인 수준 포함).

> **리서치 방법과 한계.** 리서치 렌즈는 다섯 개였습니다. Google(Trends·Trends API·Material), 글로벌 경쟁사,
> 한국 시장, 데이터 API, 데이터 시각화·UX입니다. 직접 HTTP 접속이 막혀 있어 웹 검색 결과만 썼습니다. 렌즈들이 같이 쓰는
> 검색 한도가 도중에 바닥났기 때문에 다음 내용은 이번에 다시 검증하지 못했습니다. **데이터 시각화·UX 렌즈 전부**(논문·표준을
> 기억에 의존해 정리), Wikimedia·Google Trends·KOSIS/ECOS 세부, DataLab 화면 문구·색입니다. 각 근거에는
> `확인`(1차 출처로 확인) · `유력`(신뢰할 만한 2차 출처나 확립된 표준이지만 이번에 재확인하지 못함) · `미확인`을 붙였습니다.
> 판매사가 쓴 글에는 ⚠ 표시를 했습니다(예: Exploding Topics가 직접 쓴 경쟁사 비교, 스크레이핑 API 판매사가 쓴 pytrends 소식, 제휴 리뷰).
> 이 저장소에서 직접 재거나 실험한 사실은 `[R*]`로 표시했습니다.

## 1. 누구를 위한 것인가, 핵심 Job 3개

### 1.1 사용자

| 페르소나 | 지금 쓰는 도구 | trendai에서 원하는 것 | 근거 |
|---|---|---|---|
| **P1. 마케터**(대행사·브랜드의 퍼포먼스/콘텐츠) | 네이버 데이터랩, 검색광고 키워드도구, 블랙키위, 썸트렌드, 엑셀·구글 시트 | 시즌 기획(언제 오르기 시작해 언제 정점인지), 후보 키워드 비교, 주간 리포트에 붙일 1–2줄 인사이트 | 대행사 업무 흐름: 키워드 발굴 → 추이 비교 → 시즌 기획 → 리포트 [K21]. 국내 검색 점유율은 네이버 약 63–64% [K17] |
| **P2. 셀러·MD·소상공인** | 쇼핑인사이트, 아이템스카우트, 엑셀 | 소싱·재고 판단: 이 상품군이 뜨는지, 내 매출과 검색 관심이 같이 움직이는지 | 쇼핑인사이트 TOP500으로 발굴 [K7]. 내 데이터를 검색 관심과 나란히 보는 도구는 없음 [K16] |
| **P3. 기획·전략·데이터 담당, 기자·연구자** | 엑셀 예측 시트, KOSIS·ECOS 내려받기 | KPI·지표의 추세 분해, 구조 변화 시점, 범위가 붙은 전망을 보고서에 넣기 | 엑셀 FORECAST.ETS의 기본값은 95% 구간 [C16]. 로더는 KOSIS·ECOS 날짜 형식을 이미 읽음(README) |

공통으로 가져오는 멘탈 모델은 세 가지입니다. **데이터랩**은 최대 5개 주제어, 상대값 100, 엑셀 다운로드입니다 [K1][K6]. **Google 트렌드**는 검색창 하나와 기본값 칩입니다 [G2]. **엑셀 예측 시트**는 예측선과 95% 구간입니다 [C16]. 새 개념(국면, 상승 확률, 단순 예측 대비 오차)은 이 세 모델에 비유해 설명합니다.

모바일과 PC의 역할을 나눕니다. 결과 확인은 휴대폰에서 많이 하고(네이버 모바일 이용이 PC의 3배 이상 [K19]), 비교 설정과 내보내기는 PC에서 합니다 [K21]. 그래서 **결과 화면은 모바일 우선, 업로드와 비교 편집은 데스크톱에서 가장 편하게** 만듭니다.

### 1.2 핵심 Job 3개

| Job | 사용자가 하는 말 | 성공의 정의 | 담당 화면 | 처음 묶음 기능 |

| **J2. 여러 후보 중 뭐가 뜨나?** | "패딩·플리스·경량패딩 중 올겨울 뭐에 집중하지?" | 후보 2–5개를 한 화면에서 순위(상승 점수)와 국면으로 비교하고, 카드 하나를 눌러 근거를 봄 | 홈 → 비교 결과 → 상세 | `+ 비교` 칩, 비교 차트, 순위 카드 |
| **J3. 내 매출/KPI 데이터의 추세와 전망** | "우리 월매출 엑셀 올리면 내년 상반기 범위가 나와?" | 파일을 끌어다 놓고, 감지 결과(날짜 열·값 열·주기)를 확인하고, 상세·비교 결과를 엑셀/PNG/공유 링크로 가져감 | 업로드 → 확인 → 상세/비교 → 내보내기 | 업로드·붙여넣기, 확인 단계, 내보내기 |

이 순서가 우선순위입니다. J1은 가장 자주 쓰이는 입구이고, J2는 Google·데이터랩 사용자가 이미 몸에 익힌 습관이며 [G2][K1], J3는 경쟁사가 아무도 하지 않는 차별점입니다 [C17][K16].

### 2.2 trendai가 메우는 빈자리

확인한 범위에서 다음 네 가지를 함께 하는 제품은 없었습니다 [C17][K16].

1. **설명되는 국면 판단.** 태동기·성장기·정점·쇠퇴기·안정기·재부상·변동성 판단에 숫자가 든 근거가 붙습니다. 경쟁사 라벨은 기준을 공개하지 않습니다 [C5][C11][C12].
2. **불확실성이 붙은 예측.** 80%/95% 구간, 상승 확률, 시나리오, 그리고 그 시계열에서 직접 백테스트한 정확도를 보여 줍니다. 경쟁사는 선 하나와 전체 정확도 주장뿐입니다 [C4][C9][C14]. 국내 도구는 예측 자체가 없습니다 [K16].
3. **내 데이터.** 매출·KPI·KOSIS/ECOS 내려받기를 키워드 데이터와 같은 화면, 같은 방법으로 분석합니다 [C17][K16].
4. **한국어와 한국 데이터.** 네이버 검색어트렌드, 한국어 위키백과, 만/억 표기, 국내식 등락색, CP949 엑셀까지 지원합니다. 글로벌 제품은 한국어 UI도 네이버 데이터도 없습니다 [C7][C17].

**포지셔닝 문장(내부용).** "trendai는 숫자가 *왜* 이렇게 움직였는지, *지금 어디쯤*인지, *앞으로 어디로 얼마나 확실하게* 갈지를 한국어로, 내 데이터까지 설명합니다."

```
                    출력: 설명된 판단 + 불확실성 있는 예측
                                   ▲
                                   │            ● trendai (목표)
          ○ Glimpse(예측선·계절성)  │
          ○ Exploding Topics(예측선)│
   플랫폼 데이터만 ◄────────────────┼────────────────► 내 데이터까지
          ○ Google 트렌드           │            ○ 엑셀 예측 시트(구간 O, 설명 X)
          ○ 네이버 데이터랩          │
          ○ 썸트렌드(언급량)         │
                                   ▼
                       출력: 지표·차트(해석 없음)
```

### 2.3 하지 말 것 (요약)

- 방법을 밝히지 않은 정확도 한 숫자로 광고하기, 구간 없는 예측선 [C4][C9][C14]
- 기준을 공개하지 않은 상태 라벨 [C5]
- 예측·내보내기를 유료 최상위 등급에 숨기기, 자동 결제 체험, 가입 후에만 보이는 가격 [C1][C6][C10]
- 0–100 상대 지수를 '검색량'이라고만 부르기, 서로 다른 요청의 지수를 한 축에 비교하기 [G1][K1]
- 확장 프로그램 의존, 스크레이퍼 의존(pytrends, 데이터랩 화면 스크레이핑) [G15][C8]
- 숫자 없는 AI 문단 [K12]
- 네이버를 흉내 낸 초록색 브랜딩 [K22]
- 결과 페이지 광고 [D10]

### 3.2 공통 레이아웃

- **상단 바**: `trendai` 워드마크 · 탐색 · 내 파일 · 샘플 · 방법 | `KO/EN` · 테마(시스템/라이트/다크).

- **빈 화면을 남기지 않습니다.** 예시 키워드, 샘플 9종, 업로드 카드를 처음부터 보여 줍니다. NN/g 빈 상태 원칙(상태·배울 단서·바로 가는 길) [V17], Google 홈의 출발점들 [G7], ET 온보딩 [C18]을 따릅니다. 예시 키워드는 계절성이 뚜렷한 한국 키워드로 고릅니다. 시즌 기획이 데이터랩의 주 용도이기 때문입니다 [K21].

- **입력 규칙.** 쉼표나 Enter를 누르면 별도의 비교 칩이 되고, `+`를 쓰면 같은 그룹으로 합산합니다. 칩을 누르면 '같은 뜻 검색어(쉼표로 구분)' 입력란이 열려 데이터랩 사용자는 익숙한 방식으로 그룹을 편집할 수 있습니다 [K1].
  - 이렇게 정한 이유가 있습니다. 메인 검색창에 쉼표를 넣는 사람은 대부분 비교를 원합니다(Google 습관 [G2]). 데이터랩의 '쉼표 = 합산'은 칩 편집기 안에서만 씁니다.
- **'최근 분석'은 localStorage에 저장하는 브라우저 편의 기능**입니다. 계정은 MVP에 넣지 않습니다(가입 전에 가치를 먼저 보여 줌 [C2]).
- **모바일**: 검색창을 누르면 전체 화면 검색 뷰(최근 검색 + 예시)로 바뀝니다 [G19].

  - 시계열마다 색과 아이콘을 고정하고, 차트·범례 칩·카드·표·스파크라인에서 똑같이 씁니다 [G7].
  - 예측은 같은 색 **점선**으로 그립니다. 범위 띠는 기본으로 끄고, 시계열 하나를 가리키거나 선택했을 때만 그 시계열의 띠를 보여 줍니다. 팬 다섯 개가 겹치면 읽을 수 없기 때문입니다.
  - 색이 있는 선은 최대 5개이고, 선 끝에 이름을 직접 붙입니다(dataviz: 4개 이하는 직접 라벨, 범례는 항상 둠) [V26].
  - **이중 축은 쓰지 않습니다** [V25].
- **축 규칙(`scale`)**
  1. 네이버는 한 요청 안의 ratio가 이미 같은 척도이므로 `raw`로 보여 줍니다 [K1][D3].
  2. 위키백과는 같은 단위(조회수)이므로 `raw`로 보여 줍니다. 최댓값 차이가 20배를 넘으면 `로그`를 권하는 안내를 띄웁니다.
  3. 업로드한 파일의 여러 값 열은 단위가 다를 수 있으므로 `index`를 기본으로 합니다. 첫 공통 한 주기 평균을 100으로 맞추고, "각 시계열의 2022년 평균을 100으로 맞췄어요"라고 밝힙니다 [V25][V26]. 기준값이 0 근처이거나 음수이면 index가 불가능하다고 안내하고 `raw`를 씁니다(README의 % 규칙과 같은 이유).
  - **출처가 다른 시계열은 한 차트에 섞지 않습니다**(MVP).
- **순위 카드**: `compare.rank_trends`의 상승 점수(0–100, 50 = 중립)로 정렬합니다. 다른 정렬은 상승 확률, 예측 변화, 최근 변화, 현재 수준입니다. 카드에 들어가는 것은 다음과 같습니다 [C3][G5].
  - 순위, 색 견본 + 아이콘 + 이름
  - **국면 배지**(아이콘 + 글자)
  - 전망(▲/▼/▶) + 상승 확률(말 + 숫자)
  - **기준을 밝힌** 예측 변화와 최근 변화
  - 스파크라인(실선 이력 + 점선 예측 꼬리 + 마지막 점)
  - 예측 신뢰도 칩
  - 카드 묶음 머리에 "스파크라인은 카드마다 세로축이 달라요"라고 적습니다.
- **점수 각주**: "상승 점수는 전망(예측 변화·상승 확률)과 최근 기세(최근 변화·모멘텀)를 합친 0–100 값이에요. 50이 중립이고, 예상 상승률이 아니에요."(README 정의)
- **표로 보기**: 순위 표(`rank_trends`의 열 중 이름·국면·예측 변화·상승 확률·최근 변화·모멘텀·점수)와 CSV.
- **시계열이 6개 이상인 경우**(업로드한 파일에 값 열이 많을 때): 순위는 최대 20개까지 보여 주고, 차트는 상위 5개만 색으로, 나머지는 회색으로 그립니다. 회색 선을 누르면 강조됩니다(하나만 강조하고 나머지는 회색 [V26]).
- **네이버 저검색량 경고**: 한 요청 안에서 어떤 시계열의 최댓값이 5 미만이면 그 카드에 "다른 검색어보다 검색량이 매우 적어 해상도가 낮아요"라고 경고하고 `[이 검색어만 다시 분석]` 버튼(API 1회 추가 호출)을 둡니다. ratio는 요청 전체의 최댓값 기준이라 작은 시계열은 0과 1 근처에 뭉치기 때문입니다 [K1][D3].

- **히어로**
  - 국면 배지(크게): 아이콘 + 글자. `▸왜?`를 누르면 근거가 펼쳐집니다.
  - 전망 문장: 방향 + 말로 된 가능성 + 숫자 + **비교 기준**. 비교 기준 문구는 지금 리포트가 쓰는 "(향후 12개월 평균, 최근 12개월 평균 대비)"를 그대로 가져옵니다. 상승 확률은 **예측 마지막 한 주기의 평균과 최근 한 주기의 평균**을 비교한 값이기 때문입니다 [R5].
    - **주의.** dataviz 렌즈의 초안 문구 "12개월 뒤 지금보다 높을 확률"은 trendai의 정의와 다르므로 쓰지 않습니다.
  - 예측 신뢰도 칩과 정확도 한 줄.
- **KPI 타일 6개**(모바일 2열): 현재 국면(판단 확신도 높음/보통/낮음) · 최근 변화(기간 명시) · 모멘텀(가속/둔화 + 값) · 예측 변화(기준 명시) · 상승 가능성(말 + 숫자) · **피크 시즌**.
  - 피크 시즌은 계절성이 뚜렷할 때만(`metrics.seasonal_strength` 기준) 보여 주고, 분해 결과의 계절 성분(`Decomposition.seasonal`)이 가장 높은 달/주와 오르기 시작하는 시점을 씁니다. 예: "보통 7월 정점 · 5월부터 상승". 이 값은 지금 JSON에 없으므로 서버에서 계산해 결과에 추가합니다.
  - 계절성이 없으면 이 자리에 '변동성'을 둡니다.
  - 타일마다 `?` 한 문장 정의를 붙이고 **비교 기준을 반드시 씁니다** [G21][K21].
  - %가 의미 없어 엔진이 `—`와 이유를 주는 지표(README '변화율은 의미가 있을 때만')는 타일에도 `—`와 짧은 이유를 그대로 보여 줍니다.
- **메인 차트**: 4.3 차트 관례를 따릅니다.
  - 구조 변화는 번호 배지 ①②③로 표시하고 차트 위에는 최대 5개만 라벨을 붙이며, 나머지는 아래 목록으로 보냅니다. 목록과 차트는 양방향으로 강조됩니다 [V-주석].
  - 이상치는 속이 빈 링으로 표시하고, 툴팁은 z-점수 대신 말로 씁니다("평소 범위를 크게 벗어남 · 실제 41 / 예상 25").
- **"왜 이 국면인가요?"** [C5][V18][V19]
  - **MVP**: `phase.reasons`(숫자가 든 문장)를 근거 목록으로 보여 주고, 판단 확신도와 '국면 판단 규칙 보기 › /method#phase' 링크를 붙입니다. 규칙과 임계값은 방법 페이지에 공개합니다.
  - **다음 단계**: 근거를 구조화합니다(규칙 ID · 측정값 · 임계값 · ✓/✗). 그 위에 반사실 문장을 만듭니다("최근 기울기가 0 아래로 내려가면 정점으로 바뀝니다"). 지금 `phase.reasons`는 문장 목록일 뿐 임계값 구조가 없으므로 [R3] `analysis.lifecycle_phase`에 구조화된 근거 필드를 추가해야 합니다.
- **과거**: 구조 변화 목록(날짜 · 라벨(성장 가속 등) · 변화 강도는 말로 · 차트 연결), 이상치 목록, 계절성 요약(MVP는 한 줄, 월별 패턴 막대는 다음 단계 [C9]).
  - 사용자 이벤트 메모("캠페인", "가격 인상")는 다음 단계입니다 [V-주석]. 메모는 '왜 바뀌었나'라는 질문에 답합니다.
- **미래**
  - 시나리오 상자: 비관 · 기준 · 낙관(예측 마지막 시점의 80% 하한 · 예측값 · 상한, 비교 대상 값 명시)
  - 예측표(접힘. 기간 · 예측값 · 80% · 95%)
  - **정확도 블록**: "과거 12개 시점으로 검증한 결과, 단순 예측(직전 값 유지·계절 반복·추세 연장 중 가장 나은 것)보다 오차가 23% 작았어요". 쓰인 모델은 쉬운 이름으로 적습니다. MASE 같은 기술 지표는 '자세히' 안에만 둡니다 [C4][R4].
  - **예측력이 약하면**(4.3 규칙 8): "예측력이 낮아 범위만 참고용으로 보여 드려요." [G16]
- **해석**
  - 규칙 기반 해석문을 기본으로 보여 주고 `규칙 기반 해석` 배지를 붙입니다.
  - 문장 속 숫자와 날짜는 차트 지점이나 타일로 연결합니다 [K12].
  - `[AI로 다시 쓰기]`는 사용자가 누를 때만 실행하고, 결과는 스트리밍으로 보여 줍니다. 배지는 `AI 해석 · Claude`이고, 그 아래 "AI가 작성한 해석이에요. 수치는 위 분석 결과를 근거로 해요."라고 적습니다 [V30].
  - **출처가 네이버이면 AI 버튼을 비활성화하고 이유를 밝힙니다**(5.1.6) [D10][D11].
- **주의할 점**: 해석문의 주의 항목과 고정 면책 문구 "예측은 과거 패턴이 이어진다고 가정해요. 갑작스러운 사건이나 외부 변수(가격·광고·휴일)는 반영하지 못해요."(README '한계와 주의'의 요약).

### 3.6 업로드 흐름 (J3)

```
① 올리기                ② 확인 (Datawrapper식 "이렇게 읽었어요")          ③ 결과
┌───────────────┐      ┌──────────────────────────────────────────┐
│ 끌어다 놓기     │      │ 날짜 열: [날짜 ▾]  형식: 2024.01 (월)          │
│ [파일 선택]     │  →   │ 값 열:  ☑ 매출  ☑ 방문수  ☐ 번호(제외됨: 순번) │  →  상세(1개)
│ [엑셀에서 붙여  │      │ 주기:   [월간 ▾] (자동 감지)                   │     또는
│  넣기]         │      │ 미리보기: 첫 5행 / 마지막 5행                    │     비교(2개 이상)
│ CSV·TSV·엑셀·  │      │ 안내: CP949로 읽었어요 · 빈 기간 2개를 보간했어요 │
```

- **입력**: 파일 선택, 끌어다 놓기, **엑셀에서 복사해 붙여넣기**(탭 구분 텍스트를 임시 `.tsv`로 저장해 `load_table`에 넘김). 형식, 인코딩, 날짜·숫자 표기는 README '읽을 수 있는 데이터'와 같습니다. 한도는 10 MB, 값 열 최대 20개입니다(초기값).
- **확인 단계를 반드시 넣습니다.** `load_table`이 감지한 날짜 열·형식(`series.attrs["trendai"]`), 제외한 열과 이유, `DataNotice`·`DataWarning`(안내·경고)을 그대로 보여 주고 드롭다운으로 고칠 수 있게 합니다. 감지에 실패해도(예: `no_date_col`) **막다른 오류가 아니라 이 단계에서 열을 고르게** 합니다 [V32][G9].
- **Google 트렌드 CSV 안내 카드**: "Google 트렌드 → 탐색 → 차트 오른쪽 위 다운로드(CSV) → 여기에 올리기". 출처를 'Google 트렌드(사용자 업로드)'로 기록하고 '상대 지수(0–100)' 라벨과 Google 인용 문구를 자동으로 붙입니다 [G4]. 로더 보강이 필요합니다(5.3, [R2]).
- **개인정보**
  - 원본 파일은 파싱한 뒤 바로 지웁니다.
  - 결과(JSON)는 추측할 수 없는 ID로 24시간 보관해 새로고침과 되돌아오기를 지원합니다.
  - 공유 링크를 만들면 30일 보관하고, 연장과 삭제가 가능합니다.
  - 업로드 화면에 "개인정보(이름·연락처 등)가 든 파일은 올리지 마세요. 원본 파일은 저장하지 않아요."라고 적습니다.
  - 업로드 내용은 서버 로그에 남기지 않습니다 [V-공유].

### 3.7 로딩 · 진행 상태

**측정값** [R1]: 이 컨테이너의 웜 프로세스에서 한 시계열 분석에 월 120개는 0.35–0.40초, 주 520개(≈10년)와 일 3,980개(≈11년)는 약 1초가 걸렸습니다. 따라서 다음과 같이 정합니다.

| 샘플 1개, 월간 업로드 1개 | < 1초 | 결과 레이아웃과 같은 크기의 스켈레톤만(스피너 없음) | 1초 안이면 흐름이 끊기지 않음 [V15] |
| 네이버·위키 조회 + 1–2개 분석 | 1–4초 | 스켈레톤 + 한 줄 상태("네이버에서 받아오는 중…") | 2–10초는 반복 애니메이션 [V16] |
| 비교 3–5개(주간), 업로드 여러 열 | 3–10초 이상 | **단계 진행**: ① 데이터 확인 → ② 추세·계절성 분해 → ③ 구조 변화·이상치 → ④ 예측 모델 검증 (3/5) → ⑤ 정리. 시계열 하나가 끝날 때마다 그 카드를 바로 채움 | 10초 근처부터는 단계·비율 표시 [V15][V16], 일하는 과정을 보여 주면 가치를 더 크게 느낌 [V14] |
| AI 해석(Claude) | 수 초–수십 초(측정 안 함) | 문장을 스트리밍하고, 규칙 기반 해석은 먼저 보여 둠 | |

- 화면을 점진적으로 채웁니다. 이력 + 국면 → 예측 띠 → 해석 순서입니다. 구현할 때는 `pipeline.run` 대신 `analysis.analyze → forecast.auto_forecast → compute_outlook → generate_narrative`를 단계마다 호출하고 단계 이벤트를 보냅니다(SSE 또는 폴링).
- 취소 버튼을 두고 `prefers-reduced-motion`을 존중합니다. 가짜로 시간을 맞춘 진행 막대는 쓰지 않습니다 [V16].

### 4.3 차트 관례

1. **이력**: 실선 2px `--c-hist`. 마지막 관측점에 점(8px, surface 2px 테두리)을 찍습니다.
2. **예측**: 점선 2px(대시 6 4), 단일 차트는 `--c-fc`, 비교 차트는 그 시계열의 색입니다. **마지막 실제값에서 바로 이어 그립니다**(이음새에 틈이나 점프가 없게) [V3]. 예측선을 이력보다 굵거나 밝게 그리지 않습니다.
3. **띠**: 95%(바깥, 연함)와 80%(안쪽, 진함)를 겹쳐 그리고, **이음새에서 폭 0으로 시작합니다** [V3][V4]. 범례 문구: "진한 띠: 10번 중 8번은 이 안 · 연한 띠: 95%" [V5]. 캡션: "범위가 넓어지는 건 먼 미래일수록 덜 확실하기 때문이에요. 값이 더 출렁인다는 뜻은 아니에요." [V13][V12]
4. **예측 영역**: 옅게 칠한 배경과 위쪽 '예측' 라벨, 그리고 세로 점선 '현재' 기준선(라벨 '마지막 실제값 2026.10')을 둡니다. 실선/점선 · 음영 · 라벨이라는 **색이 아닌 단서 두 개 이상**으로 예측과 이력을 구분합니다 [V20].
5. **추세선**: 1.5px 회색 **도트**(대시 1 3)입니다. 예측 점선과 패턴이 달라야 합니다. 상세에서는 켜고, 비교에서는 끕니다.
6. **미완료 기간**: **분석에 넣지 않습니다.** 네이버·위키 커넥터는 마지막으로 **완료된** 일/주/월까지만 요청합니다(위키는 이미 그렇게 함 [D14]). 그래서 Google의 '미완료 점선 = 예측 오인' 문제가 생기지 않습니다 [G20].
7. **주석**: 구조 변화는 ①②③ 배지와 가는 세로선, 차트 위 라벨은 최대 5개(2–6단어)입니다. 이상치는 속이 빈 링 8px `--c-anom`입니다. 방법이 바뀐 시점(예: 출처 쪽 변경)은 Google 'Note'처럼 날짜에 고정한 ⓘ 표시로 남깁니다 [G10].
8. **예측력 규칙**: `forecast.skill ≥ 1`(가장 나은 단순 예측보다 낫지 않음)이면 **중앙선을 지우고 띠만** 그리고, '참고용' 칩과 3.5의 문구를 붙입니다. 예측 신뢰도가 `낮음`이면(skill < 1) 중앙선을 1.5px, 불투명도 .6으로 낮추고 '참고용' 칩을 붙입니다 [G16][V6].
9. **세로축**: 음수가 될 수 없는 시계열은 `최솟값 ≤ 최댓값의 50%`일 때 0을 포함하고, 그렇지 않으면 데이터 범위를 보기 좋게 반올림합니다. 축을 끊는 표시는 쓰지 않습니다. 네이버 상대 지수는 0–100(띠가 100을 넘으면 그만큼 확장)입니다. 눈금은 데스크톱 4–6개, 모바일 3–4개입니다.
10. **가로축**: 단위와 기간을 늘 밝히고(`주 단위 · 2021.11 ~ 2026.10`), 해상도를 말없이 바꾸지 않습니다 [G11].
11. **크로스헤어·툴팁**: 날짜 · 실제값(또는 예측값 + 80% 범위) · 이상치/구조 변화 설명을 보여 줍니다. 비교 차트는 모든 시계열 값을 내림차순으로 보여 줍니다. **포커스와 탭으로도 열리고 Esc로 닫힙니다**(WCAG 1.4.13). 키보드 ←/→로 점을 이동하고 `aria-live`로 읽어 줍니다. 모바일은 **누른 채 끌기(스크럽)**이고, 손가락 밑 툴팁 대신 차트 위 고정 판독 줄을 씁니다(토스증권·Apple 주식 방식) [V20][V27].
12. **범례**: 시계열이 2개 이상이면 차트 위 칩 범례를 두고(누르면 숨김/강조), 4개 이하는 선 끝에 직접 라벨을 붙입니다. 단일 시계열은 범례 없이 제목이 이름을 맡습니다.
13. **접근성**: `role="img"`, `<title>`, 그리고 자동 생성한 1–2문장 요약을 `<desc>`로 넣습니다(예: "선크림 주간 상대 지수, 2021–2026. 매년 7월 정점. 향후 26주 평균 +18% 예상"). '표로 보기'를 두고, 선·마커·포커스 링은 3:1 이상, 누를 수 있는 대상은 24px 이상(모바일은 44px 권장)입니다 [V20][V21]. 한국 기준은 KWCAG 2.2입니다 [V29].
14. **스파크라인**: 120×32px, 축 없이 실선 이력 + 점선 예측 꼬리 + 마지막 점만 그립니다. 카드마다 세로축이 다르다는 점을 묶음 머리에 적습니다.
15. **쓰지 않는 차트**: 게이지, 파이, 도넛, 3D, 이중 축. 국면을 게이지로 그리지 않습니다 [G17].

### 4.5 문구 톤

- **안내·버튼·빈 상태·오류는 해요체**입니다. 짧은 문장, 숫자 먼저, 해결책을 함께 줍니다. 예: "값이 6개뿐이라 예측 범위가 넓어요."
- **분석문(해석문·근거·주의)은 합니다체**입니다. 지금 내러티브 엔진의 문체를 유지합니다. 예: "2023년 3월에 성장이 가속했습니다."
- **과장하지 않습니다.** '폭발', '대박', '확실'(≥90%가 아닐 때), 느낌표를 쓰지 않습니다. ET의 'Exploding' 같은 말은 번역해 들여오지 않습니다 [C5].
- **불확실성은 숫자 범위로 말합니다.** '오를 수도 있습니다'처럼 숫자 없는 표현은 범위보다 신뢰를 더 떨어뜨립니다 [V6].
- **AI가 쓴 글은 늘 표시합니다** [V30].

## 5. 데이터 출처 계획

출처 우선순위는 다음과 같습니다. MVP는 ① 위키백과(키 없음, 기본 대체 출처), ② 내 파일(Google 트렌드 CSV 포함), ③ 샘플, ④ 네이버(운영자 키가 있을 때 기본, 약관 확인 후 정식 공개)입니다. Google 트렌드 실시간 연동은 하지 않습니다.

### 5.1 네이버 데이터랩 검색어트렌드 (NAVER API HUB)

**5.1.1 엔드포인트와 인증** [D1][K8]

```
POST https://naverapihub.apigw.ntruss.com/search-trend/v1/search
X-NCP-APIGW-API-KEY-ID: <HUB 키 ID>
X-NCP-APIGW-API-KEY:    <HUB 키>
Content-Type: application/json
```

- 기존 Developers 키(`X-Naver-Client-Id/Secret`, `openapi.naver.com/v1/datalab/search`)로는 HUB를 호출할 수 없습니다 [K8]. 경로는 `/v1/datalab/search`에서 `/search-trend/v1/search`로 바뀌었습니다 [D5].
- 일정(공식 공지 미확인, 2차 출처): HUB GA 2026-06-25, Developers 신규 발급 중단 2026-07-31, 레거시 지원 종료 2027-06-30 [D6]. 구 NCP 'AI·NAVER API Search Trend'(`naveropenapi.apigw.ntruss.com/datalab/v1/search`)는 2026-07에 종료됐습니다 [D7].
- **결정**: 커넥터는 HUB를 기본으로 합니다. 환경변수 `NAVER_API_HUB_KEY_ID`/`NAVER_API_HUB_KEY`가 있으면 HUB를 쓰고, 없고 레거시 `NAVER_CLIENT_ID`/`NAVER_CLIENT_SECRET`만 있으면 레거시 경로로 대체합니다(2027-06-30까지). 키는 서버에만 두고 프런트엔드·URL·로그에 절대 넣지 않습니다.

**5.1.2 요청** [D2][K1]

```json
{
  "startDate": "2021-11-01",
  "endDate": "2026-10-26",
  "timeUnit": "week",
  "keywordGroups": [
    {"groupName": "선크림", "keywords": ["선크림", "자외선차단제"]},
    {"groupName": "패딩",   "keywords": ["패딩", "롱패딩"]}
  ],
  "device": "mo",
  "gender": "f",
  "ages": ["4", "5"]
}
```
(값은 설명용 예시입니다.)

- `startDate`·`endDate`는 `yyyy-mm-dd`이고 가장 이른 날짜는 **2016-01-01**입니다 [K4]. `timeUnit`은 `date|week|month`만 됩니다(`day`는 안 됨). `keywordGroups`는 **최대 5개**입니다.
- 그룹당 검색어 수는 HUB 문서 본문에는 20개, 같은 문서의 표에는 5개로 나와 **서로 다릅니다**. **구현에서는 5개로 제한합니다**(안전한 쪽). 20개가 확인되면 늘립니다 [D3][K2].
- `device`는 `pc|mo`(생략하면 전체), `gender`는 `m|f`, `ages`는 문자열 코드입니다: `1`=0–12세, `2`=13–18, `3`=19–24, `4`=25–29, `5`=30–34, `6`=35–39, `7`=40–44, `8`=45–49, `9`=50–54, `10`=55–59, `11`=60세 이상. **쇼핑인사이트의 10단위 코드(`10`…`60`)와 섞지 않습니다** [K5].
- `endDate`는 **마지막으로 완료된 기간의 끝**으로 정합니다(4.3 규칙 6).

**5.1.3 응답** [D3]

```json
{
  "startDate": "2021-11-01", "endDate": "2026-10-26", "timeUnit": "week",
  "results": [
    {"title": "선크림", "keywords": ["선크림", "자외선차단제"],
     "data": [{"period": "2021-11-01", "ratio": 12.37}, {"period": "2021-11-08", "ratio": 11.9}]}
  ]
}
```

- `period`는 버킷의 시작일입니다. `ratio`는 **이 요청의 결과 전체에서 가장 큰 값을 100으로 둔 상대값**이고, datalab.naver.com 화면의 결과와 같습니다 [K1][D3].
- 문서에는 `ratio`가 Number/Integer로, `keywords`가 Array/String으로 서로 다르게 적혀 있습니다. 예시는 실수와 배열입니다. **`ratio`는 실수로, `keywords`는 배열로 받고 둘 다 방어적으로 파싱합니다.**
- **값이 빠진 버킷**: 전체 기간 격자로 다시 맞추고, 빠진 기간은 0으로 채우면서 안내합니다("네이버가 값을 주지 않은 기간 N개는 0으로 처리했어요 — 검색량이 매우 적은 기간"). 빠진 버킷이 정말 0을 뜻하는지는 **미확인**입니다.
- 주간 버킷이 무슨 요일에 시작하는지도 **미확인**입니다. 응답의 `period`를 그대로 씁니다.
- 각 `results[i]`는 `pd.Series(index=period, values=ratio)`가 됩니다. `series.attrs`에 출처 메타데이터(출처, 그룹, 조건, 조회 시각, `value_kind="relative_index"`)를 넣어 출처 줄과 내보내기에 씁니다.

**5.1.4 한도와 비용** [D4][K9][D21]

- 검색어트렌드와 쇼핑인사이트는 **각각 월 50,000건**입니다(따로 셈). 키당 **50 RPS**를 넘으면 **429**가 나고, **월 한도에 닿으면 자동 차단**됩니다. 50/80/100%에서 메일이 오고, 무료 기간에는 한도를 올릴 수 없습니다.
- 지금은 '한시 무료'이고, 종량제는 미리 공지한다고 합니다. 공식 가격표는 찾지 못했습니다.
- 50,000 ÷ 30.4일 ≈ **하루 1,600건**입니다. 그래서 다음 장치를 둡니다(초기값).
  - **서버 캐시 키**: (그룹들, 검색어, 시작일, 종료일, 단위, 기기, 성별, 연령). 최근 구간을 포함한 결과의 TTL은 24시간이고, **전체 보관은 21일 이하**입니다(5.1.6).
  - **사용자별 한도**: IP당 네이버 새 조회 시간당 20건. 캐시 적중은 세지 않습니다.
  - **전역 예산 가드**: 이번 달 사용량이 80%를 넘으면 새 조회에 지연 큐를 적용하고, 90%를 넘으면 새 조회를 막고 캐시만 씁니다. 화면에는 3.8의 '한도 소진' 문구를 보여 줍니다.
  - 비교 하나 = 요청 1회입니다(5개를 한 요청에 묶음). '이 검색어만 다시 분석'(3.4)할 때만 1회가 더 듭니다.
  - (다음 단계) **BYOK**: 사용자가 자기 HUB 키를 세션에만 넣어 쓰는 방식입니다. 키는 저장하거나 로그에 남기지 않습니다.

**5.1.5 ratio를 사용자에게 설명하는 법** [K1][G1][K21]

- 차트 아래에 늘 이렇게 적습니다. "상대 지수: 이 조회에서 가장 많이 검색된 주 = 100이에요. 실제 검색 횟수가 아니에요."
- `?` 툴팁에는 이렇게 적습니다. "표시된 값은 실제 검색 횟수가 아닌 상대값이에요. 조회 기간 중 가장 많이 검색된 시점을 100으로 두고 나머지를 비율로 나타내요. **같은 조회 안의 검색어끼리만** 비교할 수 있고, 기간을 바꾸면 100의 기준도 바뀌어요."
- 네이버 결과를 처음 볼 때 한 번만 인라인 설명 카드를 보여 줍니다(닫으면 다시 뜨지 않음, localStorage).
- trendai의 변화율·국면·예측은 **척도와 무관합니다**. 상대 지수여도 '+18%'는 그대로 의미가 있습니다. 이 점을 방법 페이지에 적습니다.
- (다음 단계) **절대량 환산**: 사용자가 키워드도구의 최근 1개월 월간검색수를 입력하면 그 달을 기준점으로 지수를 비례 환산하고, 결과에 '추정치' 라벨을 붙입니다 [K7][K21].

**5.1.6 약관·표기 (보수적 기본값)**

  - 네이버 출처 시계열은 **Claude로 보내지 않습니다**. AI 해석과 질문을 비활성화하고 이유를 밝힙니다.
  - 캐시는 **21일 이하**로 둡니다. 공유 링크에는 쿼리만 담고 데이터는 담지 않습니다.
  - **원본 ratio는 내려받기에서 뺍니다**(3.10). 서비스 전체에 **광고를 넣지 않습니다**.
- NCP AI·NAVER API 약관은 사전 동의 없는 제3자 제공·재판매를 금지하고, NAVER가 지정 표기를 요구할 수 있다고 정합니다 [D12].
  - **표기**: "출처: 네이버 데이터랩 검색어트렌드(NAVER API HUB)"를 텍스트로 적습니다. 네이버 로고와 초록 브랜딩은 쓰지 않습니다(공식 서비스로 오인되면 안 됨).
- **정식 공개 전 법무 확인 항목**: 개정 특약이 데이터랩에 적용되는지, 계산값(추세·예측) 내보내기가 허용되는지, 표시 방식.

**5.1.7 오류 매핑** [D9][D4]

- HUB 공통 오류 본문은 `{"error": {"errorCode", "message", "details"}}`입니다. 검색어트렌드는 `300`(API 미사용 설정), `401`(인증 실패 — 키 오류이거나 앱에서 검색어트렌드를 켜지 않음), `500`(서버 오류)을 문서화했고, 한도 초과는 `429`입니다.
- 앱에서 검색어트렌드와 쇼핑인사이트 중 하나만 켜면 다른 쪽에서 인증 오류가 납니다. 사용자 문구는 3.8을 따르고, 상세 내용은 운영자 로그로만 남깁니다.

### 5.2 Wikimedia 조회수 (위키백과)

- **엔드포인트**(레포에서 이미 사용 중 [D14]): `GET https://wikimedia.org/api/rest_v1/metrics/pageviews/per-article/{lang}.wikipedia/all-access/user/{문서}/{monthly|daily}/{YYYYMMDD}/{YYYYMMDD}`
  - 응답은 `items[{project, article, granularity, timestamp 'YYYYMMDD00', access, agent, views}]`입니다.
  - `agent=user`이므로 봇·스파이더는 빠집니다. 데이터는 2015-07부터 있습니다(**미확인**, 이번에 재확인 못 함 [D15]).
  - 지금 커넥터의 기본 시작일은 2016-01-01이고, 마지막으로 완료된 달/일까지 요청합니다.
- **값의 성격**: **실제 조회수(원래 단위)**입니다. 출처 표시는 "출처: Wikimedia Pageviews · 한국어 위키백과 · 사람 조회만(봇 제외)"입니다. 조회수 데이터는 CC0으로 알려져 있지만 **미확인**이라 [D16] 출처는 늘 적습니다.
- **반드시 고칠 것**: Wikimedia User-Agent 정책은 연락처가 든 설명형 UA를 요구합니다 [D16, 미확인]. 그런데 지금 UA `trendai/0.1 (time-series trend analysis tool)`에는 연락처가 없습니다 [D14]. 공개 전에 `trendai-web/<버전> (<배포 URL>; <운영 연락 이메일>)` 형식으로 바꾸고, 운영자 설정값으로 둡니다. 2025년에 신원 미상 대량 트래픽 제한이 강화됐다고 하나, 구체적인 수치는 확인하지 못했습니다.
- **사용성**
  - 검색어가 아니라 **문서 제목**입니다. 404이면 `conn_no_article` 문구와 함께 제목 추천을 보여 줍니다.
  - 넘겨주기(redirect)를 정규 제목으로 풀고 자동완성을 제공하려면 MediaWiki API(opensearch / `action=query&redirects`)를 써야 하는데, 이번 리서치에서 **검증하지 못했으므로** 다음 단계로 둡니다.
  - 위키백과는 `+` 그룹 합산을 지원하지 않습니다(MVP: 문서 하나가 칩 하나).
  - 화면에 "위키백과 조회수는 관심의 대리 지표예요. 검색량과 다를 수 있어요."라고 적습니다.
- **캐시**: 월간은 24시간, 일간은 6시간입니다. CC0로 알려져 있어 보관 제약은 없다고 보지만 확인이 필요합니다.

### 5.3 Google 트렌드 — 선택 사항이고 불안정한 이유

- **실시간 연동을 하지 않는 이유**
  1. 공식 Trends API는 **알파**입니다(2025-07-24 발표). 소수의 테스터만 신청해서 쓸 수 있고, 문서조차 접근이 막혀 있습니다 [G12][G13][D17]. 테스터 보고에 따르면 `searchtrends.googleapis.com/v1alpha`의 `fetchTimeSeries`는 장기 실행 작업이고, 점마다 `search_interest`와 `scaled_search_interest`(0–100)가 있으며, 한도가 작고 실시간 인기는 없습니다 [G14].
  2. **pytrends**(지금 `trends` 커넥터가 쓰는 것)는 2025-04-17에 보관(archived)됐습니다. 비공식 엔드포인트를 쓰므로 429가 잦습니다 [G15⚠].
  3. 웹사이트 값은 요청마다 0–100으로 다시 정규화되고 표본이라 새로고침하면 바뀝니다 [G1].
- **결정**
  - (a) 웹 앱 서버는 pytrends에 의존하지 않습니다. CLI의 `trends` 명령은 그대로 둡니다.
  - (b) 'Google 트렌드 CSV 올리기' 안내 경로를 둡니다(3.6).
  - (c) 공식 알파 접근을 따로 신청하고, 승인되면 커넥터를 추가합니다(Could).
  - (d) 유료 SERP 벤더(SerpApi·DataForSEO)는 가격과 약관을 확인하지 않았으므로 [D18⚠] 도입하지 않습니다.
- **로더 보강이 필요합니다** [R2]. 이 세션에서 고전적인 Trends CSV 형식으로 실험한 결과는 다음과 같습니다.
  - 첫 줄 `Category: All categories`와 빈 줄이 있으면 `load_table`이 `no_date_col`로 **실패**합니다.
  - `<1` 값은 '숫자로 읽을 수 없는 값'으로 **결측 처리 후 보간**됩니다. 저검색량이 보간값으로 부풀려지는 셈입니다.
  - 열 이름 `sunscreen: (South Korea)`가 그대로 시계열 이름이 됩니다.
  - **고칠 것**: 머리말 줄 건너뛰기, `<1`을 0.5로 읽고 안내하기("‘<1’은 0.5로 읽었어요"), `term: (지역)`에서 검색어와 지역 분리, 출처 메타데이터에 `google_trends_upload` 기록.
  - 현재(2024년 이후) Trends 내보내기 형식과 한국어 UI 머리글은 **미확인**이므로 실제 파일로 확인해야 합니다.
- **표기**: "Data source: Google Trends (https://www.google.com/trends)"와 '상대 지수(0–100, 요청마다 다시 맞춰짐)' 라벨을 붙입니다 [G4][G1].

### 5.4 내 파일 (업로드)

### 5.6 법·정책 메모

1. **원본 데이터를 재배포하지 않습니다.** 네이버 원본 ratio는 내려받기와 공유 링크에서 빼고, 캐시는 21일 이하로 둡니다 [D10][D12]. Google 트렌드 업로드 데이터는 사용자 본인의 것이므로 내보내기를 허용하되 Google 인용 문구를 넣습니다 [G4].

3. **광고를 넣지 않습니다** [D10].
4. **AI 표시**: 생성형 AI가 쓴 글에는 'AI 해석 · Claude'를 붙입니다. 인공지능 기본법(2026-01-22 시행)에 생성형 AI 고지 의무가 있습니다. 소규모 서비스에도 적용되는지는 미확인이지만 표시합니다 [V30]. Google도 Gemini 기능을 설명하는 페이지를 따로 둡니다 [G7].
5. **업로드 데이터**: 원본을 저장하지 않고, 결과는 비공개가 기본이며 보관 기한을 둡니다(3.6). 개인정보를 올리지 말라는 안내와 `/privacy`를 둡니다. 개인정보보호법 대응은 법무 확인 항목입니다.
6. **사칭 금지**: 네이버·Google 로고나 브랜드 색을 쓰지 않고, 텍스트로만 출처를 밝힙니다.
7. **접근성**: WCAG 2.2 AA와 KWCAG 2.2를 목표로 합니다 [V20][V29].

## 8. 구현에 넘길 계약 (요약)

웹 앱은 기존 패키지를 **감싸기만** 합니다. 분석 규칙은 패키지 안에 그대로 두고, 웹 의존성은 선택 extra(`[web]`)로 분리해 패키지 본체의 `numpy`·`pandas`만 쓰는 원칙을 유지합니다.

| 엔드포인트 | 하는 일 |
|---|---|
| `POST /api/analyze` `{source, terms 또는 upload_id, options}` | 작업 ID를 돌려줌 |
| `GET /api/jobs/<id>/events` | SSE: `stage`(①–⑤, n/N), 시계열 하나가 끝날 때마다 `series_done`(그 시계열의 `report_to_json` + SVG), `done`, `error`(카탈로그 코드 + ko/en 문구) |
| `GET /api/results/<id>` | 전체 결과: 시계열별 `report_to_json(lang)`, `rank_trends` 표, 출처 메타데이터 |
| `POST /api/upload` (multipart, 붙여넣기 텍스트) | `{upload_id, detected:{date_col, date_format, value_cols, excluded, freq}, notices[], warnings[], preview}` |
| `POST /api/share` · `DELETE /api/share/<id>` | 업로드 결과 공유 링크 만들기·삭제 |
| `GET /api/export/<id>.(csv\|xlsx\|png\|html)` | 내보내기(네이버 원본 제외 규칙 적용) |
| `POST /api/narrative/<id>/<series>` | Claude 해석 스트리밍(네이버 출처는 403 + 이유 코드) |

- 차트의 첫 렌더는 `report.py`의 SVG를 재사용합니다. 크로스헤어, 키보드, 스크럽, 범례 토글은 작은 바닐라 JS로 점진적으로 더합니다.
- 숫자 표기는 서버의 ko/en 규칙 하나로 통일합니다(4.4).
- 문구는 `messages.py` 카탈로그에 화면용 코드를 추가해 관리합니다.
